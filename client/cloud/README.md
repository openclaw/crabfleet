# Account and signaling

`crabfleet-cloud` implements the independent client's account model, password/MFA requests, cloud WebSocket transport, discovered computer directory, and peer signaling selection. It builds on Linux and browser WASM and is integrated into the default egui viewer. Normal password/MFA sign-in, discovery, and peer signaling have passed live checks; see the [interoperability evidence and remaining limits](../docs/jump-interoperability.md).

## Account flow

Create `account::Account`, call `sign_in()` with user-supplied `Credentials`, and regularly call `poll()` with monotonically increasing milliseconds. The password flow uses the observed `POST https://api.jumpdesktop.com/v1/user/auth` request, the browser account scope `api-all`, and no device-token revocation. Passcode-required/invalid states allow `submit_passcode()` with either a verification code or a recovery code. CAPTCHA-required is a distinct state; the client does not solve, skip, or retry a challenge automatically. Google, Apple, company SSO, and a complete challenge handoff still need implementation.

Pending password/MFA credentials expire after two minutes and are cleared on success, rejection, sign-out, or cancellation. Individual HTTP requests have a 20-second deadline and a 1 MiB response limit. `Secret` redacts its `Debug` output and zeroes its owned Rust string when dropped; network libraries and browser internals also hold transient copies that the application cannot zero directly. Account tokens are kept only in memory. Secure session persistence is not implemented.

Native requests run off the UI thread with certificate verification and redirects disabled. Canceled results cannot return to the caller; an in-flight native request may finish until its network timeout, with at most four native account workers active. Browser requests use same-origin Fetch to `/api/jump/auth`, no cookies, no cache, redirect rejection, bounded streaming reads, and an abort controller. They explicitly select a same-origin referrer policy so Firefox preserves the real app Origin on POST instead of inheriting the page policy and sending `Origin: null`. They send the shared `Credentials` JSON shape to our [Rust web gateway](../web-gateway/README.md), which validates fields and constructs the normal fixed upstream request. Direct Fetch was ruled out after an unauthenticated preflight omitted CORS permission for `http://127.0.0.1:8093`. The gateway uses verified server-to-server HTTPS and does not change or spoof a browser origin.

## Discovery and signaling

Successful native sign-in opens `wss://neuron.jumpdesktop.com/v1/ws/neuron`; the browser opens `/api/jump/signaling` on the app's origin using the `crabfleet-jump-signaling-v1` subprotocol. Both send the account token through the observed length-delimited protobuf connect message. The gateway forwards bounded binary signaling to the same fixed service endpoint. The directory is populated from server presence announcements. Only online computers advertising both Fluid and RTC v2 can be selected through `bind_computer()`; arbitrary IDs cannot be selected. Server metadata and repeated fields have explicit bounds. Selecting a computer creates a cryptographically random connection ID. Incoming peer messages must match both that computer and the current connection ID.

The account model returns `service::Event::Signal` to the caller. Socket sends queue their failures for `poll()` rather than replacing a pending disconnect reason. A host termination received before a trailing socket failure still reaches the viewer and cancels host recovery; authentication and policy rejection remain terminal. The viewer's `jump_runtime` feeds its SDP/candidates into `crabfleet_rtc::connection::Connection`, returns that connection's outbound signals using `Account::send_signal()`, and maps advertised ICE servers into the RTC options. Account sign-out or signaling failure closes the RTC session and clears previously displayed video. Native runtime operations run on a bounded worker; browser operations run on the UI thread.

`reconnect()` replaces the socket, clears previous presence/selection, and uses the latest server-supplied tokens. It does not automatically reopen a desktop or retry rejected credentials. `sign_out()` clears the directory, selection, ICE configuration, and tokens. Server authentication rejection is surfaced to the caller. The normal signaling heartbeat is 60 seconds; the client times out initial signaling after 20 seconds and an unresponsive service after 150 seconds.

`retryable_failure()` distinguishes network loss/timeouts from rejected authentication, invalid messages, and local resource failures. Native handshake resets, timeouts, and early EOF are retryable; TLS validation errors, malformed handshakes, and authentication/policy rejection remain terminal. Already received protocol messages remain ahead of a socket-disconnect event, so a preceding authentication rejection cannot be erased and misclassified as network loss. `cancel_reconnect()` closes a pending socket while retaining the in-memory account token for a manual retry. The viewer owns the separate five-attempt/two-minute automatic recovery policy, host selection, and input fencing.

Native sockets use verified TLS, a bounded worker, nonblocking steady-state I/O, and a five-second stalled-write deadline. Browser sockets use the browser WebSocket API. Received messages have a 2 MiB plus framing limit, a 4 MiB retained payload limit, and 128 events; outgoing application queues are also bounded. Platform TLS/network buffers have their own additional limits. Native DNS resolution may outlive caller cancellation, but the result is fenced and native socket workers are capped at four.

## Verification

```bash
cargo test --locked --manifest-path client/Cargo.toml -p crabfleet-cloud -p crabfleet-fluid
cargo clippy --locked --manifest-path client/Cargo.toml -p crabfleet-cloud --all-targets -- -D warnings
cargo clippy --locked --manifest-path client/Cargo.toml -p crabfleet-cloud --target wasm32-unknown-unknown -- -D warnings
```

The HTTP integration test exchanges password/MFA requests with a local synthetic HTTP server. The WebSocket test authenticates to a local synthetic signaling server, reconstructs a split presence message, selects its advertised computer, closes, and reconnects. Gateway tests exercise the additional same-origin HTTP and WebSocket path using the shared credential and protocol types. These tests exercise actual socket I/O but do not prove vendor authentication, TLS interoperability with the vendor, browser execution, or a remote Jump desktop session. Unit tests cover token refresh, stale routing, redaction, and malformed discovery data. Research evidence and remaining acceptance requirements are in [the interoperability status](../docs/jump-interoperability.md).
