# Jump interoperability status

The independent Linux and browser clients connect to a real Jump-managed Mac using their own Rust account, signaling, and Fluid implementations. Live checks on September 14, 2026 verify password/MFA sign-in, discovery, host authentication, desktop video, pointer/Unicode keyboard input, audio output, explicit clipboard transfer, view-only suppression, and input release on both targets. Browser recovery after gateway interruption also passes. The synthetic demo remains a separate local fixture. This is experimental compatibility with the tested host, not complete vendor feature parity.

The official Windows [viewer](https://mirror.jumpdesktop.com/downloads/viewer/JumpDesktop.exe) and [Connect installer](https://mirror.jumpdesktop.com/downloads/connect/JumpDesktopConnect.exe) were downloaded for offline metadata inspection. Their SHA-256 values were `bc63d1c61983c4c2f4d4e16dcdec4d3ff274f48278da1a88a85c6fdb4f444c90` and `b5ec725299668c007e65c300b09ed1dc603fdb91e6d6e59fc3ec13d5b8739cd8`. Neither is included in this repository. The Connect installer was subsequently signature-verified and executed only in the task-owned AWS Windows lab described below; the vendor viewer was not executed. Protocol observations came from the public browser application below, followed by normal authenticated interoperability checks.

The [public browser application](https://app.jumpdesktop.com/) references [index-C2xSamZ5.js](https://app.jumpdesktop.com/assets/index-C2xSamZ5.js). The downloaded bundle is 4,605,362 bytes; its original SHA-256 is `96d1e49b39c3ec8629293c1867271deec68827e58ea374b81dea7f321a32529a`. Vendor bundles are not included in the repository.

Static inspection establishes these browser implementation facts:

- WebSocket signaling and the RTC control channel use length-delimited Protocol Buffers. Generated `connect` and `rtcproto` message definitions are present.
- Peer setup exchanges SDP and ICE candidates, opens an RTC data channel, and receives media tracks. The session uses the channel label `rtc`.
- Peer information precedes host authentication. Desktop media is requested after an access-mask update.
- The desktop request can include system audio. Input, clipboard, cursor, display selection, and stream suspension use control messages.
- Zstandard control-stream compression is negotiated; the browser can advertise no compression support.

The observed `rtcproto.ControlPeer` envelope has these field numbers:

The [documented cloud REST API](https://jumpdesktop.com/openapi/) covers team administration, device discovery, and connection links. It does not supply a complete Fluid client protocol. Account authentication, service signaling, and remote-machine authentication need separate implementations and tests.

## Independent implementation

`fluid/` implements the observed control and signaling envelopes with Protocol Buffers, bounded framing and allocation checks, host authentication state, permissions, display selection, clipboard opt-in, input release, keepalives, and stale-session fencing. Its tests use independently constructed messages. These tests establish local behavior, not live compatibility.

`rtc/` is the platform media boundary. The native implementation uses GStreamer's WebRTC stack for ICE, DTLS, SRTP, SCTP, and media decoding. Browser builds use the browser's corresponding APIs. The adapters expose bounded control/signaling events and retain only the latest decoded video frame. A passing local WebRTC peer test exchanges a fragmented control message in both directions, checks a decoded 320×180 VP8 frame, counts decoded Opus samples through a silent test sink, and verifies idempotent teardown and callback ownership. It uses no Jump account or remote host agent. See [the adapter contract and limits](../rtc/README.md).

The shared viewer connects this boundary to account authentication and discovered computers. Native and browser account connectivity, real-host video/input, audio playback, and explicit clipboard transfer are verified. The live evidence and remaining platform limits appear below.

The `rtc::connection` layer now joins WebRTC to the Fluid session state machine. A second passing native integration test follows the data-channel-first setup, synthetic host approval, media request, subsequent media renegotiation, input delivery, permission revocation, and key release. It exposed and fixed a native startup race: `webrtcbin` can request negotiation during data-channel creation before the channel is installed in application state, so the initiator also explicitly requests its first offer. This test is local protocol/transport proof and contacts no real host.

## Account and discovery implementation

The public application signs in through `POST /v1/user/auth`, handles `passcode-required`, `passcode-invalid`, and `captcha-required`, and uses its returned account token to authenticate the signaling WebSocket. The independent client's initial password flow uses the observed `api-all` scope, matching the browser account flow; it does not request device-token revocation. Third-party provider sign-in and a complete browser challenge handoff remain separate work.

Computer presence arrives as `ConnectServerMesg.presence`. Its `info` field contains exactly one length-delimited `ConnectJumpMesg` whose server-list field is 2. Server-list field 1 contains server entries; field 3 advertises connection methods (`Rtcv2 = 2`). Server entries contain a tunnel name, metadata pairs, protocol (`RTC = 3`), name, OS type, and version. These are discovery facts from the same public source, not permission to contact arbitrary IDs. The client selects only an advertised computer and keeps incoming signals bound to that peer and connection ID.

`cloud/` now implements the password/MFA request path, cancellable UI-facing account tasks, native HTTPS and browser Fetch adapters, native TLS/browser WebSocket signaling, token refresh storage, bounded computer discovery, selection, reconnect, and sign-out. The account model retains credentials only during the sign-in/MFA attempt and clears them on success, rejection, cancellation, or timeout; no credential persistence is implemented. Google/Apple/SSO and browser challenge handoff remain unimplemented. The default egui viewer now owns both this account model and the RTC session through a shared runtime.

The viewer provides password/MFA forms, computer selection, interactive host approval or requested local credentials, video presentation, physical USB keyboard/pointer input, view-only/audio controls, display selection, and explicit UTF-8 clipboard transfer. The public message enum identifies UTF-8 clipboard content as type 1. A native worker has a 128-command/4 MiB queue; only the newest video frame reaches the UI. Account/host transitions fence stale commands and images, and access revocation invalidates the displayed texture even if access is restored within the same poll. Tests cover these boundaries. A native GPU screenshot verifies the signed-out screen with no account request. Browser provider/challenge login remains work in progress.

An unauthenticated OPTIONS request to the account endpoint with the actual local app origin `http://127.0.0.1:8093`, method POST, and header `content-type` returned HTTP 204 without any `Access-Control-Allow-Origin`, `Access-Control-Allow-Methods`, or `Access-Control-Allow-Headers`. This confirms a direct browser Fetch constraint for that origin; it is not an authenticated service test. The web target now uses our own backend for normal server-to-server authentication. No origin spoofing or browser security override was used.

## Same-origin browser gateway

`web-gateway/` uses Axum/Tokio to serve the four built app assets and the browser's account/signaling endpoints. The browser's shared `Credentials` JSON is validated and normalized into the same fixed upstream `api-all` request used by the native client. Browser cookies, authorization headers, and Origin are not forwarded, and upstream cookies are not returned. The gateway enforces the configured Host/Origin, JSON schema, concurrency and byte limits, verified HTTPS/WSS, and deadlines. No upstream URL can be supplied by a request or command-line option. Tokens pass through the gateway to the browser's in-memory account model; no persistence or payload logging is implemented.

Browser signaling uses an explicit subprotocol on the app origin; the gateway opens the vendor connection only after a binary account message and relays bounded chunks in order. Media and Fluid control still use the browser's WebRTC connection directly to the authorized host. Six loopback tests cover password/MFA, request normalization and header isolation, origin/Host/schema/size/capacity rejection, fragmented presence and peer signaling, close-code preservation, shutdown, and browser cancellation during an upstream upgrade. A compiled-gateway smoke check verified health plus all four served assets byte-for-byte against `client/dist`. The complete native Rust workspace has 104 passing tests, plus five Node loader tests and a separately run native-to-Chromium control/media test. Chrome completes normal vendor password/MFA authentication, receives live computer presence through this gateway, and supports usable real-host desktop sessions as detailed below.

## Browser lifecycle

Inspection of the locked eframe 0.36.2 source showed that hidden views invoke `App::logic` without `App::ui`, and `ctx.input().time` remains that of the last visible frame. Session polling now lives in the logic hook, while the raw-input hook supplies fresh time. Texture uploads stay in the visible UI and use a single pending frame. A native egui test invokes the real logic-only path to verify snapshot updates, fresh deadlines, and capture release with no UI pass. The wrapper also supplies the downcast hook required by `WebRunner::app_mut`, preventing the exported diagnostics/input-release methods from panicking.

The loader releases input on blur/hidden events and cancels startup on pagehide. If GPU initialization completes after retirement, the resulting runner is destroyed again. Input events from before focus loss are removed before egui can replay its retained hidden-page input. On a [back/forward-cache pageshow](https://developer.mozilla.org/en-US/docs/Web/API/Window/pageshow_event), the destroyed app reloads and requires a fresh sign-in. Five Node tests cover these loader boundaries using fake page events/renderer objects. They do not execute browser WebRTC, GPU, or authentication. [Browser visibility and timer throttling](https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API) can still suspend execution entirely; live background/resume behavior remains an acceptance check.

A visible, isolated Chrome 153.0.8010.36 profile on Linux ran the built WASM app through the local gateway without browser security overrides. Its signed-out screen rendered with no page errors. The first visual check exposed light system preferences switching egui away from the configured dark widget style; selecting the dark theme explicitly in the shared constructor fixed the contrast and sizing. The corrected screenshot was visually inspected at the desktop's native 2× scale.

Two separate `wasm-bindgen-test` tests execute the actual browser WebRTC adapter in that Chrome profile. A JavaScript peer answers the initial data-only offer and echoes a fragmented Fluid message over DTLS/SCTP, then initiates media renegotiation. The adapter decodes a red 320×180 frame and receives Opus samples (checked using inbound RTP statistics), plays the audio element muted, and stops its tracks and callbacks on close. The second test closes during a pending offer and checks that asynchronous completion cannot publish events or retain the adapter. Audio generation starts through a normal browser button gesture and produces silence. No external ICE/signaling service, microphone, or desktop capture is used. These browser tests supplement the native Rust and Node loader tests. A third browser test covers service-shaped STUN configuration; a separate native-to-Chromium test verifies fragmented control echo, browser-initiated media renegotiation, decoded VP8/Opus, post-media control delivery, mute switching, and teardown. These local fixtures are distinct from the real-host acceptance below.

The same browser displayed synthetic frames and acknowledged pointer/key input. Escape released capture, and clicking/typing in view-only mode left acknowledgements unchanged at six. Calling the exported `release_input()` changed capture from true to false synchronously. Navigating away removed the demo TCP connection; browser Back started a fresh session with zero acknowledgements and no captured input. At the final pre-navigation sample, 995 frames had been received and displayed. This proves browser rendering, demo input, and navigation cleanup only; it does not exercise Jump WebRTC media, account authentication, audio, clipboard, or a real host.

## Remote cursor images

Static inspection identifies `DesktopServer.pointerUpdate` as field 3. The update contains a changed message (field 1) and image response (field 2). Cursor images carry an ID, integer hotspot, and bitmap; the bitmap has size, format (`RGBA = 1`), raw pixels, and `scaleFactor100`. The independent implementation requests image updates after view permission is granted, asks for uncached IDs, and preserves explicit visibility changes. It does not request pointer position updates.

The cache is bounded to 16 entries and 4 MiB, with at most 16 remembered outstanding IDs. Images must have valid RGBA dimensions up to 512×512, an in-bounds hotspot, exact pixel length, and a positive scale no greater than 1600; an omitted scale defaults to 100. Invalid images end the session. A late response updates its cache entry without changing the selected cursor ID. View revocation and new sessions discard the cache. The shared egui renderer applies the scale to both dimensions and hotspot and clips the cursor to the remote viewport. These are software cursors at the local pointer position; view-only remote pointer tracking is pending.

Tests cover observed wire tags, malformed geometry/pixels, cache limits, delayed replies, visibility, permission/reopen fencing, and HiDPI hotspot placement. The local GStreamer Fluid test now exchanges cursor requests and RGBA replies over encrypted SCTP and observes the stop request on view revocation. This proves local protocol delivery, not the appearance of cursors in a live Jump session or actual browser rendering.

## Network recovery

The shared runtime now retries network failure with 1/2/4/8/16-second delays, at most five attempts or two minutes. A thirty-second stable interval resets the budget. Signaling reconnect clears discovery and uses the latest in-memory account token; host recovery requires the same selected computer to be advertised and to have previously granted view permission. A replacement performs normal host authentication and starts with empty held input and clipboard state. Cancel, disconnect, and sign-out clear recovery intent. Rejected authentication, invalid protocol data, explicit host termination, and view revocation stop host recovery.

Automatic replacement increments a separate media revision carried by host commands. This prevents queued credentials, text, clipboard operations, and input from the old connection reaching its replacement while preserving the user's account epoch. Network-loss notifications preserve earlier protocol messages, and view revocation remains visible even if a later event fails the same update. Tests cover these orderings, retry exhaustion, offline discovery deadlines, cancellation, and stale commands. A loopback account test checks that abrupt socket loss permits recovery while a preceding authentication rejection does not. During a live browser session, stopping the local gateway released capture and entered bounded retry. Restarting it restored account signaling and the previously selected computer, with an empty clipboard and a fresh host-password prompt. Normal host sign-in resumed video without re-entering account credentials. Native network-failure transitions retain local integration coverage; a live native network outage has not been induced.

Native Refresh connection also passed a live check: account signaling and discovery returned, selecting the same computer required a fresh host password, video resumed, and remote clipboard retrieval still worked. View-only preference remained enabled across that replacement. Manual browser disconnect/reconnect passed separately.

## Keyboard and clipboard integration

The observed browser keyboard mapping uses USB HID usages for physical keys, and `TextEvent.text` plus `down` for committed text. `PeerInfo.supportsTextInjectUpDown` is field 7; this client requires that capability before sending text. Fluid `PeerInfo.OSType` uses Windows=0 and Mac=1, while discovery's separate OS enum uses Windows=1 and Mac=2. The shortcut code uses Fluid's enum and tests the distinction. Live testing exposed two text paths: a single character needs a down/up pair, whereas a longer string inserts on both edges. The threshold is two Unicode characters on Mac and two UTF-16 units on Windows. Those whole-string commits receive only the completed (`down=false`) event after releasing held input. A single emoji consequently receives a pair on Mac and one completed event on Windows. Unknown peers retain the paired behavior. Regression tests cover ASCII, accents, emoji, combining characters, prior key release, and view-only rejection. Live text copied back from the hosts matched the synthetic strings exactly.

The shared input controller separates local Unicode/IME commits from physical key events. It handles native key-before-text and browser text-before-key ordering, AltGr text, local preedit, committed text, bounded IME suffix replacement, intercepted copy/cut/paste events, focus loss, capability changes, and pointer motion coalescing. A complete oversized input batch is rejected and held input released. Text and paste operations release prior input before applying their action, so a rejected operation cannot leave a modifier stuck.

Paste verifies control and clipboard permissions before constructing its messages, sends UTF-8 availability/content, then issues the host's paste chord on the same ordered control stream. A local GStreamer peer test verifies Unicode down/up, clipboard-before-paste ordering, the Mac Command chord, and rejection after permission revocation. Live checks used Send/Get clipboard plus remote copy/paste in both clients. The native Copy text locally control produced the exact test string in the Wayland clipboard; Chrome's local copy/paste was checked by clearing the local field, pasting, adding a marker, and sending it back through the host. Copy/cut affect the remote clipboard, and retrieval into the local system clipboard remains explicit. Complex IME workflows, general modifier remapping, numpad identity, physical lock-key synchronization, and reserved shortcuts remain incomplete.

Local integration tests exercise two-step password/MFA HTTP requests, signaling authentication, fragmented presence delivery, computer selection, and reconnect. Unit tests cover refreshed tokens, stale peer routing, account rejection, metadata bounds, and redaction. These local tests use synthetic credentials and loopback peers.

## Live account and connection check

The independent browser client completed normal password and verification-code authentication through its Rust gateway, authenticated the service WebSocket, and displayed the account's online Fluid computers. The native Linux GPU app independently completed the same password/MFA and discovery flow through its direct HTTPS/WSS adapter. These are real account checks, separate from the synthetic tests.

The first selected-host attempt exposed a service configuration mismatch before WebRTC negotiation: one STUN URI included `?transport=udp`, which Chrome rejected. The public browser client removes this hint. The Rust browser adapter now removes that exact suffix from plain `stun:` URIs while preserving TURN transport parameters and leaving unsupported STUN queries rejected. A third real-browser test verifies peer construction with the observed shape using loopback fixture addresses. No real relay addresses or credentials are stored in test fixtures. The rebuilt client has passed all three browser tests and repeated normal account sign-in.

The corrected browser connection reached interactive host authentication and uploaded 434 video frames from the selected personal host before receiving a host termination. Input capture remained off. The live image was not visually inspected before termination, so this proves receipt and upload of host media, not a usable sustained desktop or working input. A later headless Chrome attempt signed in successfully but ended before video with host code 6, which the public enum identifies as failed interactive authentication. The viewer now preserves the separate numeric reason (error field 3) and displays distinct timeout, rejection, unavailable-user, and unsupported-approval messages. It also lets the user explicitly choose computer credentials before connecting, sending them only when local authentication is advertised. No automatic fallback follows rejection.

Subsequent Chrome sessions used normal local-computer credentials from the user's saved login. The desktop was visually inspected and remained usable for more than 12,600 received frames before a gateway interruption. Pointer interaction, physical keyboard shortcuts, committed text, view-only suppression, and Escape release were verified using temporary test documents and Spotlight. Manual disconnect/reconnect succeeded; after disconnect, the browser retained no live RTC peers. Later native and browser sessions verified exact Unicode clipboard round trips and actual audio output. Remote TextEdit spoke only the synthetic test document; per-application playback monitoring measured non-silent samples in the native client (peak 5907/32768) and Chrome (peak 5611/32768). Chrome initially appeared silent because the headless test harness supplied its default mute flag; removing that flag enabled playback without changing browser security or autoplay policy. Live network recovery passed as described above.

The initial native failure matched GStreamer 1.28.6's `No SRTP capabilities negotiated during handshake` condition. The successful Chrome session reported DTLS 1.2 with `SRTP_AEAD_AES_256_GCM`, confirming the profile mismatch. The [native media extension](../native-media/README.md) adds the RFC 7714 AES-GCM profiles to checksum-pinned GStreamer DTLS sources, using the existing OpenSSL/libSRTP implementations and correct profile-dependent key/salt lengths. It retains authentication and replay protection, removes upstream secret-key informational logging, and is loaded only for the client process. A real native-to-Chrome test explicitly verifies the AES-256-GCM profile, 73 KiB fragmented control, VP8/Opus decoding, continued control after renegotiation, mute, and teardown. With explicit receive codec preferences, the native app also passes normal real-host credentials and displays the actual desktop.

The cross-platform media check exposed an independent native bug: GStreamer 1.28's answer generator chooses an active DTLS role from `actpass` even when the existing bundled control transport is already passive. Chrome rejected that answer with a role-conflict error. The native adapter now preserves the connected transport's role across bundled media additions, without altering certificates, ICE attributes, or unrelated transports. Unit coverage checks both roles and conflicting offers; the real Chromium test now verifies media and continued control delivery. This fixes a locally reproduced renegotiation failure, not the real host's earlier missing-SRTP failure.

GStreamer's [DTLS agent](https://raw.githubusercontent.com/GStreamer/gstreamer/1.28.6/subprojects/gst-plugins-bad/ext/dtls/gstdtlsagent.c) advertises only `SRTP_AES128_CM_SHA1_80` upstream. The private extension retains that profile alongside AES-GCM; only AES-256-GCM has been explicitly verified with Chromium. Native RTP negotiation now advertises supported receive pipelines instead of accepting formats without installed depayloaders/decoders. Missing-plugin errors use fixed codec descriptions rather than exposing remote SDP or framework debug strings.

## AWS Windows acceptance, September 14, 2026

A temporary AWS EC2 Windows Server 2022 Datacenter host (build 20348, `m7i.large`) ran the official Jump Desktop Connect 10.15.23.0 installer. Its Authenticode signature validated as PHASEFIVE SYSTEMS (L.L.C), and its SHA-256 matched the installer recorded above. The host was linked through the vendor's normal single-use Connect Code flow. Account password/MFA and the task-owned Windows local account password were used normally.

A native acceptance harness using the production Rust account, signaling, Fluid, and GStreamer libraries discovered only the named lab host, authenticated, and decoded its actual 1024×768 desktop. The Notepad document was visually inspected through the native media stream. Committed text, physical copy/select-all shortcuts, explicit clipboard send/get/paste, view-only rejection, and disconnect/reconnect with fresh host authentication passed. Exact byte comparisons included accents, a single emoji, combining characters, and a full sentence. The test exposed and fixed duplicate Windows insertion: the whole-string threshold is two UTF-16 units, unlike Mac's two Unicode characters. The native harness is library-level acceptance, not a separate proof of every egui control against Windows.

Edge 148.0.3967.70 on that Windows host also passed all three actual WASM WebRTC adapter tests: fragmented encrypted control, media renegotiation with VP8/Opus reception, teardown and stale-callback fencing, and service-shaped STUN configuration. Silent audio generation started through the normal visible test button. These fixtures use local peers and are separate from the authenticated Windows desktop session. The VM has no audio endpoint, so audible playback from a Windows host remains unverified.

Firefox 154 on a second AWS Linux desktop completed normal account password/MFA, discovery, Windows computer-password authentication, actual desktop rendering, pointer interaction, Unicode typing, explicit clipboard send/get/copy, paste, Escape release, view-only suppression, and manual disconnect/reconnect with fresh host credentials. Remote text matched the expected UTF-8 bytes exactly, including an emoji and combining accent. The view-only preference survived reconnect. This tests the shared egui web interface against Windows as well as the native library path above.

That acceptance exposed two Firefox differences. Inheriting the gateway page's `no-referrer` policy made its same-origin authentication POST carry `Origin: null`; the browser request now explicitly uses `same-origin` referrer policy, consistent with the [Fetch origin-header rules](https://fetch.spec.whatwg.org/#append-a-request-origin-header). The gateway still rejects null and foreign origins. After authentication, Firefox decoded the live video but its playback-quality frame count stayed at zero, a [known MediaStream limitation](https://bugzilla.mozilla.org/show_bug.cgi?id=1586505). Rendering now uses `requestVideoFrameCallback`, retaining at most one request and cancelling it on track replacement or teardown. The real-media regression forces a zero quality counter and checks callback cancellation and ownership.

The Linux AWS image has no GPU. Firefox rendered through Mesa llvmpipe; Chrome disabled WebGPU/WebGL on this image, so its full viewer could not run there without changing browser policy. All three rebuilt WASM tests also passed in Firefox. Its media fixture needed the image's missing PulseAudio service, kept running across test loads; the standard null sink suffices for generated silence. The fixture uses port 3478 because Firefox blocks port 9. These lab constraints do not establish hardware-accelerated performance or audible Windows-host playback.

The updated workspace passes 104 Rust tests, five Node loader tests, native and WASM clippy with warnings denied, and native/web builds. The separately ignored native-to-Chromium integration test retains its earlier passing evidence; it was not rerun for the text-edge change. Temporary host credentials, account tokens, vendor binaries, and proof captures are kept outside source control.

## Compatibility limits

Completion requires the independent client to sign in through the normal authorized account flow, discover the user's computers, establish a session, and show their actual desktop with working input on both Linux and a real browser. Audio, clipboard, view-only controls, input release, reconnect, and teardown must work with appropriate bounds and permission handling. Builds and meaningful interoperability tests must be reproducible.

Browser networking and media need platform adapters; compiling Rust to WASM does not provide native sockets. The native implementation must likewise supply WebRTC and media decoding. A vendor wrapper or RFB-only replacement does not meet the goal. Current native demo tests do not prove any of these Jump capabilities.

The tested Mac supports real sessions on both targets, including video/input, audio output, explicit clipboard transfer, view-only controls, and input release. The AWS Windows acceptance above extends native and Firefox host coverage to Windows Server 2022 and browser adapter coverage to Edge. Browser automatic recovery is verified against Mac; native network-failure behavior has local test coverage. Google/Apple/SSO and browser challenges, audible Windows-host playback, TURN-only traversal, complex IME workflows, remote pointer tracking in view-only mode, and suspended-browser recovery remain outside the verified surface. Multi-monitor selection is implemented but has not been exercised against a live multi-monitor host. Media currently copies RGBA into the shared GPU texture; zero-copy decoding and release packaging remain future work. The client is experimental and has not been published.
